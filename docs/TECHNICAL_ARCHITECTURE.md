# Technical Architecture

## 1. System Overview
Hiruna Clip has two execution domains:
- Muse / Clip Director: intelligence and reasoning.
- PC Renderer: deterministic media processing and encoding.

Flow:
User -> Muse -> Clip Manifest -> Human Review -> PC Renderer -> Final MP4.

## 2. Muse Responsibilities
Muse owns metadata discovery, transcript acquisition/cleanup, audio analysis orchestration, candidate detection, context expansion, boundary selection, semantic scoring, deduplication, ranking, and manifest generation.

Muse does not own final video encoding, GPU rendering, FFmpeg command construction, or automatic final approval.

## 3. Model / Provider Layer
The agent and model are separate concepts. The agent controls workflow; a model provides reasoning.

V1 should use one working provider first. Provider abstraction and 9router fallback can be introduced later without changing the manifest contract.

For long videos, transcript analysis should be staged/chunked to control context and token cost.

## 4. Intelligence Artifacts
The V1 intelligence contract consists of:
1. transcript.json
2. audio_events.json
3. clip_manifest.json

Schemas live under docs/schemas/.

They separate semantic evidence, deterministic audio evidence, and AI-selected production candidates.

## 5. Transcript Pipeline
subtitle source -> parse cues -> remove overlap/duplication -> preserve timestamps -> transcript.json.

Timestamp fidelity is mandatory.

## 6. Audio Pipeline
source audio -> deterministic feature extraction -> signal event detection -> audio_events.json.

Future audio ML can be added without changing the Clip Manifest contract.

## 7. Candidate Intelligence
Transcript evidence + audio signal map -> potential moments -> context expansion -> boundary selection -> semantic scoring -> deduplication -> ranking.

Event and clip are different concepts: an event must be expanded into a complete, self-contained clip.

## 8. PC Renderer
The renderer owns media acquisition, source caching, cutting, 9:16 conversion, caption generation/burning, encoding, and output validation.

It consumes selected manifest entries, not natural-language instructions.

## 9. Media Strategy
Analysis source and production source are logically separate. Use the lightest practical source for analysis and the best practical source for final production.

V1 favors a simple reliable full-source download before selected cuts rather than premature range-request optimization.

## 10. Manifest Transport
V1 does not require a web API. A local file-based contract is enough:

manifest.json -> human selection -> renderer input.

Future transport may use shared folders, local API, Telegram, queues, or a web UI. Transport must not alter the schema.

## 12. Security
- Never execute arbitrary shell commands generated by the model.
- Validate URLs and file paths before media tooling.
- Treat downloaded media/subtitles as untrusted input.
- Keep secrets/provider credentials outside Git.
- Validate manifest before rendering.
- Do not commit source media, subtitle dumps, or rendered output.

## 13. Observability
Eventually log source identification, transcript availability, audio analysis duration, candidate count, scoring decisions, selected IDs, render duration, and failures.

V1 may use structured local logs.

## 14. Non-Negotiable Principles
1. AI decides; code executes.
2. Muse is the Clip Director.
3. PC is the Worker/Renderer.
4. Manifest is the contract.
5. Human approval precedes final rendering.
6. Transcript and audio are first-class evidence.
7. Candidate event and final boundary are different.
8. Rendering does not consume LLM tokens.
9. V1 prioritizes reliability over premature distributed optimization.
